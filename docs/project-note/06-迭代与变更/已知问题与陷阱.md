# 已知问题与陷阱

每条都附**证据位置**。这些是"看起来能跑、上线才炸"的坑。

> 本仓库当前没有 `memory/` 目录，本页是唯一的长期陷阱清单。后续 `fix-bug-workflow` Step 9.2 晋升的已验证 lesson 追加到这里。

## 1. NUL 字符会让终态事务整体回滚

**症状**：任务永远停在 `running`，daemon 反复重试也进不去终态。

**原因**：`error` / `work_dir` / `session_id` / `result` 任一含 `\u0000` → PostgreSQL SQLSTATE 22P05 → 事务回滚。

**规避**：新增任何字符串字段必须同步加进 `sanitizeTaskCompleteRequest` / `sanitizeTaskFailRequest`（`handler/daemon.go:4896-4910`）。Chat 消息侧同理（`daemon.go:5872-5884`）。

## 2. 终态回调返回 400 = daemon 永久放弃

**症状**：后端认为任务失败但状态没落库，daemon 不再重试。

**原因**：daemon 把 400 视为永久错误。

**规避**：业务失败一律 **5xx**（`handler/daemon.go:4984-4989`、`:5740-5744`）；已终态则按幂等成功返回 `transitioned=false`，不要报错。

## 3. claim 代际 CAS 在三处必须同步

**症状**：`409 task claim is stale`，或任务被两个 daemon 同时跑。

**原因**：`start` 必须回传 `runtime_id + dispatched_at`（纳秒精度要与 PG 对齐）；重投、取消、start 全靠 `dispatched_at` 做 CAS（`agent.sql:874-890` 的 requeue CAS、`:1002` 的 start lock）。

**规避**：改这三条写路径中的任一条，必须同时检查另外两条。

## 4. `waiting_local_directory` 两边都是例外

**症状**：agent 显示 idle 却领不到新活。

**原因**：`FailStaleTasks` 故意排除它（`agent.sql:1256` 的 `FailStaleTasks`，注释在 `:1283-1287`），但 `CountRunningTasks` 仍把它算作占用容量（`agent.sql:1672` 的 `CountRunningTasks`）。

**规避**：排查"没活干"时先看该状态下的任务数。

## 5. 重新分配不取消正在跑的任务

**症状**：issue 改派给别人后，旧 agent 仍在跑并回写结果。

**原因**：`#4963`/MUL-4113 的既有行为（`service/issue.go:4405-4418`）。

**规避**：需要停止旧工作时显式取消任务，不要依赖改派。

## 6. Triage 对派生触发是硬拒

**症状**：新接入的触发源（插件、webhook、渠道）在 Triage 列上完全没反应。

**原因**：`ErrIssueInTriage`（`task_triage_guard.go:70`）只对 `origin == OriginNamed` 放行（`:85`）。

**规避**：新触发源必须正确设置 origin 标签，这是最容易漏的一步。

## 7. WebSocket 扇出的隐性成本（MUL-5492）

**症状**：一次描述自动保存把两份完整描述广播给工作区所有连接。

**原因**：转发器复用生产者 payload，`prev_description`/`prev_title` 也上了线。

**规避**：新 payload 的大字段必须登记到 `internalOnlyPayloadKeys`（`cmd/server/listeners.go:38`）。这是**声明式表而非 if**，因为问题是结构性的：下一个大字段会静默继承同样成本。

## 8. chat 私有事件漏投 = 内容泄漏或完全收不到

**症状**：会话内容被其他成员看到，或用户自己看不到。

**原因**：`isChatPrivateEvent` 覆盖所有 `chat:*` 与带 `chat_session_id` 的 `task:message`；缺 `ChatSessionOwnerID` 时是**丢弃**而不是放宽（`listeners.go:284-296`）。

**规避**：新增 chat 类事件必须带齐 owner 与 workspace；不要"为了不丢"改成工作区广播。

## 9. 重放窗口要求下游幂等

**症状**：Pod 重启后用户收到已读过的回复。

**原因**：sharded relay 从 `now - ReplayGrace`（默认 5 分钟）读起，会重复投递。

**规避**：所有消费者必须幂等；WeCom claim TTL 必须长于 replay grace（`sharded_stream_relay.go:37-40`、`relay_outbound.go:79-90`）。

## 10. `NEXT_PUBLIC_API_URL` 带路径会双写 `/api`

**症状**：所有请求变成 `/api/api/**`，avatar/attachment 404。

**原因**：客户自己拼 `/api`、`/uploads`、`/ws` 前缀（GH #6619）。

**规避**：该变量只给 origin。带 `/api` 结尾会被防御性剥离，其它路径原样保留。

## 11. dev 环境把 `process.env.PORT` 当后端端口

**症状**：Next dev 模式下所有 rewrite 指回前端自己。

**原因**：Next 在求值 `next.config.ts` 前写 `process.env.PORT` 为前端监听端口。

**规避**：只用后端专属别名（`BACKEND_PORT`/`API_PORT`/`SERVER_PORT`）作为回退（`apps/web/config/runtime-urls.ts:70-87`）。

## 12. Desktop 的 router 只有 Coordinator 能写

**症状**：点了没反应，也没有报错。

**原因**：绕过 `NavigationAdapter` 的跳转被判协议错误并**静默 reconcile**（`tab-coordinator.ts:19-21,280-305`）。

**规避**：只用 `useNavigation()`/`<AppLink>`。ESLint 只覆盖具名导入与 `router.navigate` 形态，别名导入、`useSubmit`、`platform/**` 内部都不受约束。

## 13. 重新赋值 workspace 造成的 setState-during-render

**症状**：React 19 报错或切工作区时状态错乱。

**原因**：`setCurrentWorkspace` 的副作用（通知 + rehydrate）都会 `setState`。

**规避**：副作用已延迟到 microtask（`packages/core/platform/workspace-storage.ts:34-75`）；不要再在 render 期直接触发订阅者。

## 14. 被伪造的 actor 头

**症状**：agent 冒充成员执行人类专属操作。

**原因**：`X-Actor-Source`/`X-Agent-ID`/`X-Task-ID`/`X-User-ID` 的安全依赖**中间件剥离**；`resolveActor` 的 header pair 兜底被明确标注"不是安全边界"（`handler/handler.go:879-896`）。

**规避**：新增路由组或绕过 `middleware/auth.go`/`daemon_auth.go` 的入口，必须自己完成剥离。

## 15. 两处方向相反的 fail 语义

**症状**：Cloud 抖动时席位仍可超卖，或 issue 上限莫名消失。

**原因**：`seatcapacity` fail-closed（`NewUnavailable`），`entitlement` fail-open（任何故障 → `ActionOff`）。

**规避**：判断"策略失效该放行还是拒绝"前先确认在哪一侧（`entitlement/README.md:80-82`）。

## 16. 令牌与权限的缓存滞后

| 对象 | 滞后 | 位置 |
|---|---|---|
| PAT 撤销 | 10 分钟 | `auth/pat_cache.go:17` |
| 成员移除 | 5 分钟 | `auth/membership_cache.go:19,27-30` |
| 会话登出 | **无撤销**，直到 `exp` | `auth/session.go:14-22` |

**规避**：安全事件响应不要只依赖"撤销后立刻失效"。

## 17. Slack 媒体守卫最弱

**事实**：WeCom 与 DingTalk 在**连接层**做地址白名单（覆盖重定向与 DNS 重绑定，`wecom/media_guard.go:14-27` 设计说明 + `:257-262` 逐地址校验；`dingtalk/media.go:182`）；Slack 只做主机名 allowlist + HTTPS（`slack/media_ingest.go:6-12`）。

**规避**：涉及 SSRF 的改动优先复用 WeCom 的连接层守卫实现。

## 18. Go 测试共享数据库的断言陷阱

**症状**：本地全绿、CI 随机红。

**原因**：所有 DB 测试共享一个库、包间并行执行。

**规避**：只断言自己 fixture 的行（状态/`pending`/`settled` + 自己的 ID），**绝不断言调用总数或返回结果长度**。

## 19. `make up` 启动了 `go run` 的 daemon

**症状**：daemon 注册成功、心跳正常，但每个任务都 `fork/exec …/go-build…/exe/multica: no such file or directory`。

**原因**：daemon 记录自身可执行路径并 re-exec 自己作为 environment helper；`go run` 的临时二进制在启动器退出后消失。

**规避**：全栈联调用 `make up C=api,web,daemon`（它从 `server/bin/multica` 启动）。

## 20. 在 agent 任务目录里操作你自己的 daemon

**症状**：任务里跑 `multica daemon stop` 把自己的 daemon 停了。

**原因**：CLI 会检测 `.multica/daemon_task_context.json` 标记并拒绝 `daemon start/stop/status`（例外：dev-env 注册表分配的显式 profile）。

**规避**：这是刻意的保护，不要尝试绕过。
