# 外部渠道机器人接入

用户在 Slack / Lark(飞书) / WeCom(企业微信) / DingTalk(钉钉) / Telegram 里 @机器人，消息如何变成一次 agent run 并把回复送回原渠道。

## 触发点

- **入站传输各异**，但都汇入同一个 `InboundHandler`：适配器在构造期注入，自己推消息（`integrations/channel/handler.go:30`；设计说明 `channel/channel.go:31-33`）。
- **前置条件**：installation 存在且启用 → 租约由本副本持有 → 消息未被去重 → 群聊里 @了 bot → 发送者已绑定 Multica 账号 → 有 invoke 权限。

## 数据流路径

```
渠道事件（WS 长连 / Socket Mode / 长轮询 / Stream WS）
  → 适配器解析 → InboundMessage
  → engine.Router.Handle（engine/router.go:209）
     ├─ /new、/clear 等命令语义解析
     └─ dispatch（router.go:301）
        ① installation 路由校验（:306）
        ② 两阶段去重 Claim（:325）——失败即当重复丢弃
        ③ 群聊 @bot 过滤（:365）
        ④ 发送者身份 + 成员校验（:372）
        ⑤ invoke 权限（:393）
        ⑥ EnsureSession / StartSession（绑定到 chat session）
        ⑦ 追加消息 + 同事务 Mark 去重（engine/session.go:565）
        ⑧ /issue 命令 → 建任务而不是对话
        ⑨ debounce → EnqueueChannelChatTask（router.go:1064）
  → （复用 Chat 链路）任务执行 → 流式消息
  → OutboundReplier.Reply（engine/resolvers.go:432）
  → 各渠道出站（HTTP API 或同一 WS socket）
```

## 关键节点详解

| 节点 | 文件位置 | 核心逻辑 | 异常处理 |
|---|---|---|---|
| 适配器契约 | `channel/channel.go:34-76` | `Type/Connect/Disconnect/Send/Capabilities` | 连接失败由 supervisor backoff 重连 |
| Supervisor | `engine/supervisor.go:279-388` | 按 installation 枚举、租约 CAS、构建 Channel、重连 | renew 失败立即拆连接（`:736`） |
| 租约 | `engine/supervisor.go:88-104,190-194` | TTL 180s、poll 30s、renew 60s；跨副本至多一个活连接 | Redis 不可用时**不启动**（fail-closed） |
| 去重 | `pkg/db/queries/channel.sql:1048-1087` | `Claim` 只回收 60s 前未 processed 行，每次 claim 换 token；`Mark`/`Release` 按 token 围栏 | token 失配 → `ErrClaimLost` → 丢弃当重复 |
| 拒绝即终态 | `engine/router.go:378-406` | 身份/权限拒绝也返回 `finalizeMark` | 改策略后同 message id **不会重试** |

## 各渠道的传输差异（同一契约，不同实现）

| 平台 | 入站 | 出站 | 关键约束 |
|---|---|---|---|
| Slack | Socket Mode WS（app-level token） | 无状态 HTTP `chat.postMessage` | 媒体只做主机名 allowlist + HTTPS（`slack/media_ingest.go:6-12`（文件头注释），最弱的一处） |
| Lark / 飞书 | WS 长连（`/callback/ws/endpoint` 引导） | 无状态 HTTP + 可选 markdown card | 大陆飞书与海外 Lark 按 installation 自动识别 |
| WeCom | aibot WS 长连（subscribe + stream 帧） | **无 REST**，必须同一 socket；`Send` 返回 `ErrSendNotSupported` | 见下节单副本约束 |
| Telegram | `getUpdates` 长轮询（50s hold） | HTTP Bot API | 409 = 有两个消费者 |
| DingTalk | Stream-mode WS | HTTP + EventHandler 风格 sender | 独立实现的媒体守卫 |

## 单副本约束（WeCom）

- WeCom 出站只有「持有该 installation WS 连接的副本」能送达；其它副本靠 `RelayOutbound` 转发 + Redis claim 去重（`wecom/relay_outbound.go:511,1067-1136`）。
- 无 Redis 或 legacy relay 时跨副本回复被丢弃，计 `no_live_connection`（`wecom/outbound_outcome.go:35-41`）。
- `.env.example` 明确要求：**启用 WeCom 时后端跑单副本**，直到跨副本出站路由落地。
- 流式气泡同样绑定单一写者（`wecom/stream_store.go:14-16`）。

## 异常路径

| 异常类型 | 处理方式 | 用户可见结果 |
|---|---|---|
| 同一消息重复推送 | `Claim` 拦下，当重复丢弃 | 无重复回复 |
| 租约续不上（脑裂） | 主动断开 WS，避免双写 | 短暂离线后重新抢租约 |
| Redis 不可用 + 要求 redis 租约后端 | supervisor 不启动（fail-closed） | 该渠道整体不可用，日志明确 |
| 群聊未 @bot | 过滤，不建会话 | 不响应 |
| 发送者未绑定账号 | 返回绑定引导 | 提示绑定流程 |
| 媒体 URL 指向内网 | 连接前地址白名单拒绝（`ErrMediaAddrBlocked`），重定向/重绑定都覆盖 | 附件下载失败，消息其余部分正常 |
| 权限被拒 | 记终态，不再重试 | 明确拒绝消息 |
