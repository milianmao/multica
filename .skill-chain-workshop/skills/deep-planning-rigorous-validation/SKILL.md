- **设计理念**：本技能受 Andrej Karpathy 理念启发，旨在通过系统性引导，将 AI 从盲目执行的助手，重塑为严谨自主的工程师。
- **核心目标**：确保任何代码变更在合并前，必须通过结构化的深度规划、实现和验证。

## 链式调用模式

本 Skill 支持三种启动模式，启动时根据调用来源自动判定：

- **🆕 v3.4 SubAgent 入口模式（来自 feat-design-planning-v3 的 Agent 工具 spawn）**：使用干净上下文，读取 SubAgent prompt 中指定的文档路径 + 项目基线，从阶段 1 开始。**不继承需求分析的对话历史**。每阶段完成后向 Main Agent 报告进度。
- **🆕 v3.4 SubAgent 入口模式（来自 deep-planning 内 Gate 失败触发 fix-bug）**：使用干净上下文，读取 Gate 失败描述 + 相关文件路径，从 fix-bug-workflow 步骤 0 开始。**不继承需求分析或代码实现的对话历史**。
- **独立调用（用户在对话中直接 @skill）**：正常执行完整流程，包括前置知识库感知。保持现有行为不变。

### 🆕 v3.4 启动模式检测逻辑

```
启动时检查启动来源:
  ├── 启动 prompt 包含 "### 必读文档" 区块 → SubAgent 入口模式 (feat→deep-planning)
  ├── 启动 prompt 包含 "### Gate 失败详情" 区块 → SubAgent 入口模式 (deep-planning→fix-bug)
  └── 否则 → 标准模式 (用户直接调用)
```

# 核心原则：从"指令执行"到"目标驱动"

Karpathy 曾一针见血地指出当前 AI 编程的问题所在："模型会替你做错误假设、不会管理自己的困惑、该澄清的时候不澄清、会把代码越写越复杂、还会顺手改掉自己并不理解的东西"。为系统性地对抗这些倾向，本技能将 Karpathy 总结的四项原则贯穿于工作流的每个阶段，其核心内涵如下：

-----

### 1. 编码前思考
**不要假设。不要隐藏困惑。呈现权衡。**LLM 缺少"疑惑"这种元认知，常默默选择一种解释并执行。本原则强制你在编写任何代码前，明确推理、暴露不确定性，将"我想当然"转变为"我验证过"。
*   **核心要点**：明确说明假设，存在歧义时不默默选择；如有更简单方法应提出；指出不清楚地方并要求澄清。

### 2. 简洁优先
**用最少的代码解决问题。不要过度推测。**LLM 在引入抽象和防御性代码时常显"品味"不足，导致代码臃肿。本原则强制你对抗过度工程化倾向。
*   **核心要点**：不添加未要求的功能、抽象、灵活性；不为不可能的异常做错误处理；能用 100 行实现，绝不写成 1000 行。检验标准是：资深工程师会觉得这过于复杂吗？

### 3. 精准修改
**只碰必须碰的。只清理自己造成的混乱。**LLM 常弄不清改动边界，习惯性地顺手改动无关代码或语义注释。本原则强制你像外科手术般精确编辑。
*   **核心要点**：不主动改善相邻代码、注释或格式；不重构没坏的东西；匹配现有风格；因你改动而产生的孤儿代码，必须删除。检验标准是：每一行修改都应能直接追溯到用户的请求。

### 4. 目标驱动执行
**定义成功标准。循环验证直到达成。**LLM 缺乏"验收标准"这一概念的易错点。本原则要求你将模糊的指令式任务（"添加验证"）转化为可验证的声明式目标（"为无效输入编写测试并让它们通过"），以此引导 AI 进行自我修正。
*   **核心要点**：将"让它工作"转化为"编写测试并让测试通过"。对于多步骤任务，也应说明简短的计划，并为每个步骤设定明确的验证点。

-----

下表为本技能之各阶段（门禁）与上述 Karpathy 四原则之间的对应关系，便于查阅与理解：

| 原则 | 映射到的门上与流程说明 |
| :--- | :--- |
| 编码前思考 | 阶段 1（需求重述与范围界定）、阶段 2（系统影响分析）、阶段 3（数据流设计） |
| 简洁优先 | 阶段 2（系统影响分析）、阶段 5（代码实现计划）、阶段 6（代码编写与自查） |
| 精准修改 | 阶段 5（代码实现计划）、阶段 6（代码编写与自查） |
| 目标驱动执行 | 阶段 5（测试用例表）、阶段 7（接口/服务 E2E 验证）、阶段 7b（用户界面验证）、**阶段 8b（需求-实现覆盖度审计）**、**阶段 8c（实现完整性审计）**、**阶段 8d（契约一致性审计）**、**阶段 8e（一键综合验证）**、**阶段 8f（业务验证审计）**、阶段 9（集成验证报告） |
| 所有四个原则 | 阶段 4（设计审核）、阶段 8（代码审核） |

## Superpowers 技能嵌入映射

本技能的关键阶段**必须调用**对应的 superpowers 子技能来执行，而非让 AI 自由发挥。每个 superpowers 子技能自带结构化思维框架和强制门禁，确保执行质量：

| 本技能阶段 | 调用的 Superpowers 技能 | 调用理由 |
|-----------|------------------------|---------|
| 阶段1: 需求重述 | `superpowers:brainstorming` | 结构化需求探索、意图澄清、消除歧义——而非 AI 自己猜 |
| 阶段5: 实现计划 | `superpowers:writing-plans` | 结构化计划分解、依赖分析、可执行步骤——而非空泛的"改这几个文件" |
| 阶段6: 代码编写 | `andrej-karpathy-skills:karpathy-guidelines` | 强制简洁优先、精准修改、不猜测——杜绝顺手重构和过度工程化 |
| 阶段7: 接口/服务 E2E 验证 | `superpowers:verification-before-completion` | 强制"证据优先"——必须拿出实际调用输出/响应体/日志，不能"看起来对了" |
| 阶段7b: 用户界面验证 | Playwright MCP（适用于 Web UI）或项目对应 UI 自动化工具 | 真实用户界面环境验证关键交互、渲染和错误状态 |
| 阶段8: 代码审核 | `superpowers:requesting-code-review` | 正式代码审查框架、结构化检查清单——而非走过场式的"看起来没问题" |

**调用规则**：
1. 以上阶段**不可跳过**对应的 superpowers 技能调用（L1 任务阶段5/6/8 仍需调用）
2. L2/L3 任务的阶段7 必须调用 `superpowers:verification-before-completion`，并根据项目形态执行真实端到端调用（HTTP API、CLI 命令、SDK 调用、消息队列事件、后台任务等）
3. L3 任务且涉及用户界面变更时，阶段7b 必须执行 UI 自动化验证（Web 项目优先 Playwright；移动端/桌面端/CLI 按项目既有工具替换）
4. **L3 任务在阶段8之后必须执行阶段8b/8c/8d/8e，不可跳过**
5. AI 在进入这些阶段时，必须先使用 `Skill` 工具调用对应的 superpowers 技能，再执行该阶段

## 前置步骤：项目知识库感知（所有级别通用）

在进入任务分级和阶段流程前，**必须先调用 query-knowledge 检索项目知识库**以快速理解项目架构、设计模式、编码规范和现有约定。这是"编码前思考"原则的落地——不了解系统就开始规划，等于闭着眼睛做设计。

**执行内容**：
1. **调用 kb-aware 一次完成 overview + search**（🆕 v3.6 D2/T3 修复，替代原 overview+search 两次调用）：
   ```bash
   python3 skills/query-knowledge/scripts/query_knowledge.py \
       --repo . --backend project-note --json \
       kb-aware --task-keywords "<任务关键词>" --task-id "$TASK_ID"
   ```
   返回 `{overview: {kb_root, kb_source, cached}, search: {hit_count, hits, cached}, cache_path, kb_content_hash}`。
   - `overview.kb_source: auto-detect` / `config-file` -> KB 可用，继续步骤 2
   - `overview.kb_source: not-found` -> 记录"本项目暂无知识库"，跳到步骤 5
   - `overview.cached: true` 或 `search.cached: true` -> 复用上游 feat-design/team 的检索结果（缓存命中，跳过实际检索，节省 ~1.5k tokens）
   - 缓存路径：`control-plane-state/session-drafts/$TASK_ID/kb-cache.json`（无 TASK_ID 时用 `.runtime/kb-cache.json`）

   根据任务类型选择关键词：
   - 架构/设计相关 -> "架构 分层 设计模式 关键决策"
   - 状态/数据相关 -> "状态管理 数据模型 Schema 持久化"
   - 组件/模块相关 -> "组件 模块边界 服务 依赖"
   - 通信/接口相关 -> "API IPC SDK 消息 事件"
   - 编码规范相关 -> "开发规范 测试 CI 发布"
       返回 top-5 相关 L3 文档（含 score / matched_sections / snippet），仅 read top-1~2 全文。

3. **CLAUDE.md 仍需手动 read**（项目级硬约束，query-knowledge 不覆盖）

4. 在后续阶段中应用知识库信息：
   - **阶段1（需求重述）**：用知识库中的术语和模块名精确描述需求范围
   - **阶段2（影响分析）**：对照知识库中的模块/组件/服务/数据/接口清单，逐项评估影响
   - **阶段5（实现计划）**：遵循知识库中的设计模式和编码规范制定计划
   - **阶段8（代码审核）**：用知识库中的规范作为审核基准

5. 如果没有项目知识库（`kb_source: not-found`），记录"本项目暂无知识库"，按常规流程继续

**输出**（记录在阶段1产物中）：
```
知识库查阅记录:
- 知识库位置: <overview 返回的 kb_root 或"不存在">
- KB 来源: <auto-detect / config-file / not-found>
- 已检索关键词: [列表]
- Top 命中文档: [path + score + snippet]
- 关键发现: [与本任务相关的架构约束/设计模式/编码规范]
- 已知模式匹配: [是否匹配知识库中记录的任何已知模式/陷阱]
```

## 任务分级（按复杂度自适应）

在进入阶段流程前，必须先对任务进行分级。分级标准如下：

| 级别 | 判定条件 | 执行阶段 | 适用场景 |
|------|---------|---------|---------|
| **L1 微小** | 涉及 ≤1 个文件、0 个设计决策、改动 <20 行 | 阶段1 → 阶段5 → 阶段6 → 阶段8（精简） | typo 修复、日志调整、单行配置 |
| **L2 中等** | 涉及 2-5 个文件、1-3 个设计决策 | 阶段1 → 阶段2 → 阶段5 → 阶段6 → 阶段7 → 阶段8 → 阶段9 | 单模块功能、小重构、API 调整 |
| **L3 大型** | 涉及 >5 个文件、>3 个设计决策、跨模块/架构变更 | 全部阶段（不可跳过任何门禁，含阶段7b、**阶段8b/8c/8d/8e**） | 新功能、架构重构、数据模型变更 |

**阶段适用规则**：
- 阶段7（接口/服务端到端验证）：L2/L3 必须执行；L1 跳过
- 阶段7b（用户界面验证）：L3 且涉及用户可见界面变更时必须执行；无界面项目可标记 N/A 并说明替代验证；L1/L2 默认跳过
- **阶段8b（需求-实现覆盖度审计）**：L3 必须执行；L1/L2 可选但强烈建议。**本阶段是防止"实现偏离需求"的第一道后置门禁。**
- **阶段8c（实现完整性审计）**：L3 必须执行；L2 涉及新增模块/文件时必须执行。检查代码、测试、配置、迁移、文档、入口注册是否齐全。
- **阶段8d（契约一致性审计）**：L3 必须执行；L2 涉及跨边界调用时必须执行。检查接口、类型、schema、事件、配置、错误码等契约是否端到端一致。

### 阶段3：数据流设计【编码前思考】
- **动作**：逐步骤描述数据从触发点到最终存储/返回的完整路径，包含每个环节的**数据格式**、**转换逻辑**、**验证规则**、**异常处理**。
- **复杂度阈值**：
  - **数据流节点 ≤2 个**：一句话描述即可（如"用户输入 → 写入数据库"），不需要形式化图表

- **产出**：

  **数据流图示例**：
  ```
  请求方 → [接收输入](认证/授权、参数格式校验) → [业务处理器]
         → [读取/调用依赖资源] → [执行业务规则] → [开启一致性边界]
         → [写入状态/数据] → [提交变更] → [发送事件/通知]
         → [返回结果给请求方]
  ```
  **数据约束表片段**：
  | 节点 | 变量名 | 类型 | 必填 | 验证规则 |
  |------|--------|------|------|----------|
  | 请求入口 | payload.amount | decimal | 是 | >0 且不超过业务上限 |
  | 状态更新 | resource.status | enum | 是 | 只允许合法状态迁移 |

### 🆕 阶段8b：需求-实现覆盖度审计（门禁3b）🔍【v3.0 新增】

> **⚡ 为什么这一步至关重要？**
>
> Stage 7/7b 验证了"代码能跑"，Stage 8 验证了"代码写得好"。
> 但**没有任何一个阶段验证了"所有原始需求都已实现"**。
> v2.0 中多个任务出现"实现偏离需求"的根本原因，就是缺少这个门禁。
>
> **本阶段强制逐条对照原始设计文档，检查每一项需求是否在最终实现中得到了满足。**

- **定位**：聚焦**"需求是否完整实现"**——从原始设计文档出发，逐条校验最终实现。
- **适用条件**：L3 任务必须执行。L1/L2 任务强烈建议执行（可精简为"检查原始需求清单上的每一项"）。
- **通用性要求**：审计项必须从当前任务的需求/设计文档中提取，禁止写入任何特定项目的固定接口、页面、表名或业务对象。

#### 执行步骤

**Step 1: 提取需求清单**

读取原始需求来源（优先级顺序）：
1. 上游设计阶段产出的设计文档和规划任务文档
2. 当前版本/迭代目录中的设计文档、规格文档或任务拆解文档
3. 用户直接提供的需求描述文本
4. 项目内明确记录的待办、验收标准或需求说明

从设计文档中提取**所有可验证的需求条目**，分类为：
- **接口/入口**：每个 HTTP 路由、CLI 命令、SDK 方法、消息主题、后台任务或公开函数
- **用户界面**：每个页面、视图、命令界面、弹窗、表单或可见状态
- **核心功能**：业务流程、数据处理、状态机、调度逻辑、权限/校验规则
- **交互行为**：按钮、快捷键、表单提交、确认流程、加载/错误/空状态
- **数据/契约**：数据结构、字段、schema、事件 payload、配置项、迁移
- **非功能需求**：性能、安全、兼容性、可观测性、可访问性、迁移/回滚

**Step 2: 逐条验证**

对每个需求条目，执行验证：

| 验证方式 | 适用于 | 具体操作 |
|---------|--------|---------|
| 真实调用 | 接口/命令/方法/任务 | 实际执行并检查响应、退出码、状态或事件 |
| 代码审查 | 核心功能 | Grep/Read 搜索函数、类、关键逻辑确认存在性 |
| 界面检查 | 用户界面 | 打开页面或运行界面，检查可见元素和状态 |
| 契约检查 | 数据/接口/事件 | 检查 schema、类型定义、payload、配置或文档 |
| 运行结果检查 | 非功能需求 | 检查日志、指标、耗时、资源或错误记录 |

**Step 3: 标记状态**

每个需求条目标记为以下状态之一：

| 状态 | 含义 | 判定标准 |
|------|------|---------|
| ✅ 已实现 | 完整实现 | 功能存在且可通过测试 |
| ⚠️ 部分实现 | 功能存在但不完整 | 如"API 存在但前端未接入" |
| ❌ 未实现 | 完全缺失 | 代码中找不到对应功能 |
| ➖ 不适用 | 该需求与本迭代无关 | 明确在 MVP 范围外或已推迟 |

**Step 4: 计算覆盖率 + 判定**

```
覆盖率 = ✅ 数量 / (✅ + ⚠️ + ❌ 数量) × 100%
```

**门禁判定**：
- **覆盖率 ≥ 95% 且 无 ❌ (P0/P1) 项** → ✅ 通过，进入阶段9
- **覆盖率 ≥ 85% 但存在 ❌ 项** → ⚠️ 列出缺口，自动回到阶段5制定补充计划
- **覆盖率 < 85%** → 🚫 驳回，必须回到阶段1重新评估需求范围
- **存在 P0 缺口（核心接口/界面/功能缺失）** → 🚫 无论如何都必须修复

**Step 5: 缺口修复循环（🆕 v3.6 按缺口类型分流，V5 修复）**

发现的缺口按以下方式处理：

**Step 8b.0: 缺口类型判定**（每个 ❌ 或 ⚠️ 条目必须先标类型）

| 缺口类型 | 判定标准 | 执行器 |
|---------|---------|--------|
| **缺实现**（`missing`） | ❌ 未实现（代码完全缺失）/ ⚠️ 部分实现但**无可观察错误行为**（只是功能不完整） | 实现补全 SubAgent（deep-planning 精简模式） |
| **有缺陷**（`defective`） | 功能已实现但行为错误--能描述"错误行为" + 复现步骤，red-capable 可建立 | fix-bug SubAgent（原 v3.4 逻辑） |

**混合情况优先级**：若 ⚠️ 部分实现中存在**任何可观察的错误行为**（返回错误值/崩溃/UI 显示异常），优先归 `defective`（走 fix-bug SubAgent，red-capable 可建立）；只有纯缺失（代码完全不存在）或「功能不完整但已有部分行为正确」才归 `missing`。判定不清时默认归 `defective`（fix-bug 的 red-capable 验证会暴露真实类型）。

**为什么必须分流（V5 根因）**：fix-bug-workflow 的 Step 1 铁律是"没有 red-capable 命令不能进 Phase 2"。"缺实现"缺口没有"坏的行为"可以复现（只有"缺失的功能"），red-capable 循环建不起来，fix-bug SubAgent 会卡在 Step 1 试图复现一个不存在的 bug。只有"有缺陷"缺口才适合 fix-bug。

### 🆕 阶段8c：实现完整性审计（门禁3c）📦【v3.1 新增，v3.4 增强契约 wiring】

> **⚡ 为什么这一步至关重要？**
>
> 阶段8b 验证了"需求是否实现"。但即使每条需求都有代码对应，仍可能存在：
> - 新增模块没有在 `__init__.py` / `AppConfig` / `create_app_container` 中注册
> - 新增文件缺少对应测试文件
> - 契约中定义的 SSE 事件有后端发射但前端 switch-case 没消费
> - 契约中定义的 TypeScript 类型没有实际 import/使用
>
> **本阶段用机械 checklist + grep 验证实现的结构完整性。**

- **定位**：检查代码、测试、配置、迁移、文档、**契约 wiring** 是否齐全且结构一致。
- **适用条件**：L3 必须执行；L2 涉及新增模块/文件时必须执行。

#### 执行步骤

**Step 1: 文件清单核对**

从阶段5实现计划中提取预期变更文件清单，与 `git diff --name-only` 实际变更对比：
- 是否有计划外文件被修改？（精准修改原则）
- 是否有计划内文件遗漏？（未实现）

**Step 2: 注册/入口核对**

对每个新增模块/类/函数，检查：
- `__init__.py` 是否导出？
- `AppContainer`/`create_app_container` 是否实例化并注入？
- 前端路由/组件是否在 router 中注册？
- CLI 命令是否注册？配置项是否在 `config.yaml` + Pydantic model 中定义？

**Step 3: 测试覆盖核对**

对每个新增/修改的源文件，检查是否有对应测试文件存在。

**Step 4: 🆕 v3.4 契约 wiring 核对（机械 grep 验证）**

> **这是 v0.17.0 缺陷驱动的新增步骤。** 契约规范定义了接口 ≠ 代码实现了接口。本步骤用**确定性 grep 命令**逐项验证，不依赖推理。

从契约规范文档 (`docs/v<version>/契约规范.md`) 中提取契约检查清单：

**4a. SSE 事件发射端验证**

对契约规范中定义的每个 SSE 事件类型，在后端代码中搜索发射点：

```bash

grep -rn "type.*<event_name>\|'<event_name>'" src/ --include="*.py"
# 期望: 至少 1 处 yield {"type": "<event_name>", ...} 或等价发射
```

**4b. SSE 事件消费端验证**

对契约规范中定义的每个 SSE 事件类型，在前端代码中搜索消费点：

```bash
# 对于每个契约事件名，执行:

```

**4c. TypeScript 类型定义验证**

对契约规范中定义的每个 TypeScript 类型/接口，检查是否实际定义和引用：

**4d. Python 类型定义验证**

对契约规范中定义的每个 Python dataclass，检查是否定义和引用：

```bash

```

**4e. 配置项 wiring 验证**

对契约规范中定义的每个新配置项，检查 config.yaml 和 Pydantic model 中是否都已注册：

```bash

```

**4f. 错误码 wiring 验证**

对契约规范中定义的每个新错误码，检查代码中是否有对应的 raise/return：

```bash
grep -rn "<ERROR_CODE>" src/ --include="*.py"
```

**Step 5: 标记状态**

每个契约项标记为 ✅ (wired) / ❌ (not wired) / ➖ (N/A 纯后端/纯前端无跨端消费):

| 状态 | 含义 | 检查方式 |
|------|------|---------|
| ✅ Wired | 发射端 + 消费端都存在 | grep 两端都有命中 |
| ⚠️ Partial | 一端有另一端无 | 如"后端发射 summary 事件但前端无 case 'summary'" |
| ❌ Not Wired | 两端都不存在 | 契约定义了但代码完全没有 |
| ➖ N/A | 纯后端实现无前端消费，或反之 | 契约中已声明责任边界 |

**Step 6: 计算覆盖率 + 判定**

```
契约 wiring 覆盖率 = ✅ 数量 / (✅ + ⚠️ + ❌ 数量) × 100%
```

**门禁判定**：
- **覆盖率 = 100%** → ✅ 通过
- **覆盖率 ≥ 90% 且无 ❌ 项** → ⚠️ 列出缺口，补完后再通过
- **覆盖率 < 90% 或存在 ❌ 项** → 🚫 驳回，必须回到阶段5补充计划

### 🆕 阶段8d：契约一致性审计（门禁3d）🔗【v3.1 新增，v3.4 增强契约 wiring 交叉验证】

### 阶段 8f：业务验证审计 GATE（唯一业务质量入口）

**触发条件**：项目存在当前版本的 SDD 或核心业务流目录时必须检查输入完整性。两者都不存在才可跳过；只存在其一不是跳过理由，而是 `BLOCK`，必须补齐文档或明确从项目范围移除业务质量链路。

**定位**：阶段 8f 不能自行拼接 Contract/Scenario、pytest 和引擎命令。唯一允许的交付入口是 `ai-quality-engine/scripts/business-quality-gate.py`；它在不可复用 run 目录中生成当前 Oracle、只运行当前生成的测试、写入 pytest 证据、调用真实业务验证器，并以 `--strict-gate` 取得唯一结论。

#### Step 0：选择当前输入与真实验证器

1. 选择一个明确的当前 SDD 文件：`docs/vX.Y.Z/契约规范.md`。禁止 `docs/v*/契约规范.md`，因为 glob 展开为多个文件会破坏输入唯一性。
2. KB 固定为目录：`docs/project-note/03-核心数据业务流/`。禁止使用不存在的单文件 `03-核心数据业务流.md`。
3. 列出本轮实际变更涉及的业务入口源文件作为 `--target`。
4. 为项目的公开入口准备无 shell 验证命令：真实 CLI、HTTP、app factory 或公开模块入口任选其一。验证器必须写入 `BUSINESS_QUALITY_VERIFY_EVIDENCE`，满足 `business-verification-v1`，包含当前 run id、SDD/KB/目标代码 hash 与至少一个已通过的业务断言。

没有真实入口验证器时，只能运行 `schema-only` 发现 Oracle 缺口；其结果固定为 `BLOCK`，不得以生成测试全绿转入阶段 9。

#### Step 1：执行统一门禁

```bash
python3 skills/ai-quality-engine/scripts/business-quality-gate.py \
  --project-root . \
  --sdd docs/vX.Y.Z/契约规范.md \
  --kb docs/project-note/03-核心数据业务流/ \
  --target <本轮业务入口源文件> \
  --output-dir tests/oracle \
  --run-id <本轮不可复用ID> \
  --evidence-level code-verified \
  --verify-command "python3 <真实业务验证器>.py"
```

`--verify-command` 传入可执行程序及参数，不得使用 `;`、`&&`、管道或重定向把任意 shell 片段拼入门禁。命令成功退出但未产生合法业务断言证据，仍是 `BLOCK`。

**纯前端/纯后端（无跨端契约）**：本次改动明确无 API/SSE 变更时用 `--no-sdd` 显式声明（不能省略），KB 与真实验证器仍必须提供；SDD 已存在但本次未涉及契约时，仍用 `--sdd` 传当前版本契约文件：

```bash
python3 skills/ai-quality-engine/scripts/business-quality-gate.py \
  --project-root . \
  --no-sdd \
  --kb docs/project-note/03-核心数据业务流/ \
  --target <本轮业务入口源文件> \
  --output-dir tests/oracle \
  --run-id <本轮不可复用ID> \
  --evidence-level code-verified \
  --verify-command "python3 <真实业务验证器>.py"
```

**`--sdd` 版本归属（自动校验）**：门禁要求契约文件 H1 首行版本号（`# vX.Y.Z 契约规范`）与父目录名 `docs/vX.Y.Z/` 一致，防止旧版本契约被当作本轮证据。

**`--changed-files` 防漏检（推荐）**：传入本轮 `git diff --name-only` 结果，门禁校验其中的业务入口文件（`.py/.ts/.tsx/.js/.jsx`，排除 tests/*.test.*/*.spec.*）都已列入 `--target`：

```bash
  --changed-files "$(git diff --name-only)" \
```

门禁自动完成以下步骤，编排 Skill 不得重复实现或替换：

1. 从当前 SDD 与 KB 生成 Contract/Scenario manifest（`--no-sdd` 时契约 manifest 标记 `declared_skipped`，不产生 O-CONTRACT-GAP，但 scenario 与真实验证照常）；
2. 为本轮 manifest 绑定 SDD、KB、目标代码 hash、evidence level 和 run id；
3. 只执行本 run 的 `contract/test_*.py` 与 `scenario/test_*.py`，写入 `pytest-results.json`；
4. 校验真实验证器写入的 `business-verification.json`；
5. 调用本仓 `ai-quality-check.py check --profile code-verified --strict-gate --format json`；
6. 写入 `gate-result.json`，输出唯一 `PASS` 或 `BLOCK`。

#### 判定、留痕与回流

| 结果 | 退出码 | 后续动作 |
|---|---:|---|
| `PASS` | 0 | 将 run id、命令、`gate-result.json` 路径和 zero blocking findings 写入 `08-gates.md`，才可进入阶段 9 |
| `BLOCK` | 3 | 进入 fix-bug-workflow；不得通过人工解释 JSON、忽略 O-* finding 或复用旧 run 放行 |
| 参数错误 | 2 | 修正 SDD、KB、target、run id 或验证器输入后，以新 run id 重跑 |

`BLOCK` 包括 extractor 失败、非法或空 manifest、当前 Oracle pytest 失败、真实验证缺失/失败/hash 不匹配、`schema-only`、`aggregate_status != valid`，以及 `O-CONTRACT-GAP`、`O-SCENARIO-GAP`、`O-MOCK-CEILING`、低 coverage、`O-TEST-FAILURE`。Critical finding 不得被总分抵消。

**结果写回（硬性）**：必须将以下内容追加到 `docs/vX.Y.Z/08-gates.md` 的 `08f` 条目：完整 run id、实际命令（敏感参数脱敏）、退出码、`gate-result.json` 路径、evidence level、PASS/BLOCK、blocking findings 与回流链接。未写回等同未执行。

**跳过记录**：仅当 SDD 与 KB 目录均不存在时可标注 `08f 跳过：无契约/KB 文档`；不得把缺其中一项、无法提供真实 adapter 或 schema-only 结果写成跳过。

## Karpathy 哲学的运行检验
对应文章所设想的"如果看到以下情况，说明这些指南正在发挥作用"，我们设置了以下判断标准：
- diff 中不必要的改动更少 —— 所有修改都能直接追溯到用户的请求。
- 因过度复杂而导致的重写更少 —— 代码第一次就写得足够简单（"Just enough code"）。
- 澄清问题在实现之前提出 —— 而不是在犯错之后。
- 干净、精简的 PR —— 没有顺带的重构或"改进"。
- **🆕 需求与实现一一对应 —— 每一条原始需求都能在最终代码中找到对应的实现。覆盖率 < 95% 的交付不被接受。**
